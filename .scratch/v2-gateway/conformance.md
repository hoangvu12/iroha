# v1 conformance checklist

Every case of kind **a** (essential) or **b** (provider quirk) in `docs/research/v1-case-catalog.md`, mapped to the v2 test that covers it, or marked not applicable with the reason. Kinds c (workarounds for v1's design) and d (dead code) are left out, as the spec says. Built by ticket 26; keep it current when a ticket changes a mapped behaviour.

## How to read it

- **v2 test(s)**: `package TestName`, or `package TestName/"subtest"` for a case of a table test. The package is the directory under `internal/` (`cmd/iroha` for the binary). Abbreviations: `T/"x"` = `rules TestBuiltinQuirkRulesClassifyTheRecordedBodies/"x"`; `G/"x"` = `rules TestBuiltinRulesClassifyTheGenericFailures/"x"`. Two quirk cases are both named "bare 402": Go runs the MiniMax one as `bare_402` and the Mistral one as `bare_402#01`. Golden translation cases are `translate TestGolden/"<case>"` (files in `internal/translate/testdata/golden/`). Every name was checked against the code when this file was written (ticket 26 kept the script that checks them outside the repo; grep a name to confirm).
- **Status**:
  - `covered`: a test asserts the behaviour (for rows the catalog marks "v1 BUG/GAP", the correct behaviour).
  - `partial (#NN)`: some of the behaviour is asserted; the rest is ticket NN.
  - `open (#NN)`: not built or not tested; ticket NN.
  - `n/a`: the case does not apply to v2; the note says why (out of scope in the spec, a v1 mechanism v2 does not have, or a v1 script replaced by an admin route).
  - `ui (#NN)`: a UI behaviour, owned by UI ticket NN (no DOM tests; the API behind it is mapped where it exists).
- **Note**: what is asserted, and `deviation:` where v2 deliberately behaves differently from v1. The deviations worth an Owner decision are collected below.

**Totals:** 521 cases (418 of kind a, 103 of kind b): 399 covered, 95 n/a, 17 ui, 5 partial, 5 open.

## Deviations for the Owner to decide on

Deliberate differences from v1 that the tests assert as they are. Each is defensible, but the Owner may prefer v1's behaviour; changing one is a small ticket.

**History and logs**
- LOG-10, USE-66: retention minimum is 1 day; v1 allowed 0 to turn Request history off (ticket 19).
- FAIL-09, FAIL-131…133, LOG-06: every failed Attempt stores the upstream body (64 KiB) and headers whole, with no redaction of `sk-…` or `Bearer …` in case a Provider echoes a key.
- RED-01, REQ-34, REQ-98, FAIL-100…102: the upstream's error message reaches the Caller inside Iroha's envelope (v1 sent stable codes only on chat routes and relayed the upstream envelope verbatim on `/v1/messages`).
- LOG-15: Audit Entries are never cleared.

**Failure handling and Key States**
- FAIL-17: Z.ai 1311 (model not in plan) is a Model Gap and the Request tries other keys; v1 stopped the Request (ticket 07).
- FAIL-18, FAIL-05, FAIL-47, FAIL-70: Z.ai 1315 (wrong product), DashScope key restrictions and account-condition 403s mark the key invalid until a test passes; v1 cooled it for 30 s (ticket 07).
- FAIL-01, FAIL-15, FAIL-59, FAIL-71, FAIL-73: cooling is 60 s doubling to 1 h; reset times the Provider reports are honoured up to 7 days (v1 clamped to 900 s); billing refusals cool the whole key 15 min; a bare 402 cools the key.
- FAIL-16, FAIL-42, FAIL-51, FAIL-75: 5xx and overload retry elsewhere with the Key State unchanged and one replay last (v1 cooled typed 5xx for 30 s).
- FAIL-103: a key whose cooling ended is tried after healthy keys (ticket 26) but gets no single-trial claim.
- PRV-32, PRV-33, PRV-38: a passing key test clears invalid and any cooling, billing included; there is no "activate" without a test.
- FAIL-80, FAIL-84…86: 3 Attempts and one 60 s first-byte deadline per Request (95 s ceiling), no rounds; v1 walked every key for up to 120 s.

**Streams and answers**
- REQ-66, REQ-73, REQ-76: a Chat stream the Provider ends cleanly without any `finish_reason` is closed with one (ticket 16); a stream that breaks off still ends with an error event, never an invented finish. Catalog: "don't invent an end".
- REQ-72, FAIL-90, TIME-06: a failure after the first byte ends with the Shape's error event, not a silent close.
- TIME-03, PRV-55: no idle limit once bytes flow; a stalled but open upstream is kept until the Caller leaves (ticket 17: long thinking pauses must survive).
- REQ-04, MOD-06…08: every answer names the model the Caller asked for (qualified on global routes), never the upstream's (ticket 32 records the upstream's on the Attempt as `reported_model`).
- REQ-85, REQ-88: `<think>` text is lifted only when it opens the answer; text after echoed reasoning is kept (ticket 16).
- REQ-17: `Accept: text/event-stream` is sent upstream on stream requests (v1 sent `application/json`).
- REQ-57, REQ-45: an Anthropic `search_result` block reaches other Shapes as text (v1 dropped it); JSON-schema keywords an Anthropic Endpoint cannot take move into the description instead of the Request being refused (ticket 30).

**Configuration and models**
- PRV-75: `POST /api/providers` with a taken handle updates that Provider (create-or-update) instead of 409; the ticket 22 create dialog must check the handle first.
- PRV-06: plain `http://` Endpoints are accepted with no opt-in.
- PRV-31, MOD-45, MOD-47, USE-69: adding a Provider or key triggers no test and no discovery; a new Provider is first refreshed within the hour.
- MOD-21, MOD-37: unlisted models are forwarded unless the Provider is `strict`.
- MOD-73: models.dev facts under the Provider's brand win over the maker's own facts (the reverse of v1).
- MOD-43, MOD-44, MOD-56, MOD-57: no templates; Z.ai's discovery URL and the DashScope / Z.ai model lists come from the Owner or the ticket 27 import.
- MOD-61: removing the "added" flag from a model discovery still lists keeps it visible; the audit outcome is `deleted` (a model with no flags does not exist for audit).

**Owner access**
- AUTH-07: one global sign-in lock (10 failures in 15 min) rather than per IP: anyone can keep the Owner out of the UI for 15 min (Admin Tokens still work).
- AUTH-10: sessions last a fixed 30 days (v1: sliding 7 days).
- AUTH-02, AUTH-03, AUTH-16: no setup or recovery tokens; an Admin Token sets or resets the Owner password.
- AUTH-13, AUTH-14: no CSRF token; SameSite=Strict plus refusal of `Sec-Fetch-Site: cross-site`.
- KEY-01, KEY-02, PER-05, PER-08: Gateway Keys, Admin Tokens and Upstream Keys are stored readable (ADR-0006) and reads are not audited.
- MGMT-01, MGMT-04: Admin Tokens never expire and can create other Admin Tokens.
- KEY-14: an active Gateway Key can be deleted without revoking it first (v1: 409 `gateway_key_active`), and the delete is revertible (ticket 24); history keeps its name and ID.
