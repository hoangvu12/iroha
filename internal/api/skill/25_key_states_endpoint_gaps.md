## Endpoint Gaps

An Upstream Key works on every Endpoint of its Provider unless restricted. When a Provider refuses a key as `invalid` on one Endpoint (a 401, or any Failure Rule whose outcome is `invalid`, your own rules included) and the key has worked on another Endpoint it may still use, Iroha does not make the key invalid: it records an **Endpoint Gap** on that Endpoint. The key keeps its Key State, is no longer sent to that Endpoint, and keeps serving the others; the Request that was refused moves on to the next candidate, as with `retry_elsewhere`. A key that has worked nowhere else becomes `invalid` as before, and a key refused on the last Endpoint it worked on becomes `invalid` and loses its Endpoint Gaps. Keyless keys are unchanged: their 401 is `retry_elsewhere`.

- **Where a key worked**: each key lists `worked_on` (`endpoint`, `succeeded_at`): the latest 2xx Attempt or passing key test per Endpoint, written at most once a minute. A new secret forgets it.
- **Seeing gaps**: each key lists `endpoint_gaps` (`endpoint`, `endpoint_id`, `reason`, `rule`, `request_id`, `created_at`) in `GET /api/providers/<handle>/keys`. `GET /api/providers/<handle>/endpoint-gaps` (`?endpoint=`, `?upstream_key=`) lists a Provider's, and the summary includes them. The route preview reports such a key as skipped with `reason: endpoint_gap` and the `endpoint`. The Attempt keeps outcome `invalid`; its `action` says "Endpoint Gap on <endpoint>".
- **Clearing**: gaps never expire. They clear when a key test passes on that Endpoint (`POST .../keys/<key>/test?endpoint=<name>`), when an Attempt there succeeds (a test chat pinned to the key and Endpoint), when the key's secret or Endpoint restriction is edited (not a rename, enable or disable), when the key becomes invalid, or by hand: `POST /api/providers/<handle>/keys/<key>/clear-endpoint-gaps` (`?endpoint=` for one) or `POST /api/providers/<handle>/keys/bulk/clear-endpoint-gaps` `{"items": [...]}`. Clearing by hand and through an edit is audited; reverting the Audit Entry restores the gaps.
- **Restricting a key to where it works**: `POST /api/providers/<handle>/keys/<key>/restrict-to-working-endpoints` (or `.../keys/bulk/restrict-to-working-endpoints`) sets the key's restriction to the Endpoints it may use minus those it has a gap on. That is a restriction edit, so it clears the gaps; one Audit Entry, and its revert restores both the old restriction and the gaps. It answers `unchanged` for a key with no gap and `409 no_working_endpoint` when the key has a gap on every Endpoint it may use. Both take `dry_run`.
- **Logs**: `endpoint_gap` events (`op` created or cleared, `upstream_key`, `endpoint`, `reason`), linked to the Provider and the Request that caused them.
- A key test without `?endpoint=` runs on the first Endpoint the key may use and has no gap on.
