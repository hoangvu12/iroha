## Decisions worth knowing

**Base URLs carry `/v1`.** `upstreamUrl()` in `src/inference/generic-adapter.ts` joins
`baseUrl + '/chat/completions'` verbatim. The manifest's `baseUrl` has no `/v1`; every stored
base URL here does.

**Wire spelling is `requested`, not `upstream`.** The manifest's `verified[].upstream` is what
the response body *claimed*; `verified[].requested` is the string that actually produced
200 + text. The rewrite map is built from `requested`. Where one canonical id answered under
several spellings, preference order was: exact canonical id, then a bare id with no slash,
then a prefixed id, then an `auto/*` router combo. Alternates are listed per id in the report's
"Model shelf" section.

**`relay-router-musa-clickconvites-com-br` is https on 443, not the manifest's http/80.** The
origin answers `http://router-musa.clickconvites.com.br/v1/...` with `308 Permanent Redirect`
to https, and iroha does not follow redirects (`redirectAllowSameOrigin` is off). relay-hunt's
probe followed it silently, which is why the win was recorded on port 80.

**Dedupe.** By normalized endpoint, never by name. `52.66.181.17` appears twice in the
manifest; it is one Provider with two Upstream Keys, each carrying its own base URL override.
Rerun: `--apply` on the current state produces zero writes (19 endpoints unchanged).

**Verification mints nothing.** The Owner-session admin test route was used instead of a
temporary Gateway Key, so no credential was created and none was left behind.

  `["muse-spark-open","muse-glimmer"]`, the original two rewrites.

Reason: `muse` cannot route anything. Every id on it — including ids it shipped with before

allow-lists, and stored availability wins. Adding capacity to `muse` therefore adds nothing.

## iroha bug worth fixing

`ModelCatalogService.discoverMissingKeys` (`src/models/catalog-service.ts:371`) writes Key Model
Availability for newly added keys after only checking the template's `modelAvailability`. It does
not check the Provider's `modelDiscovery`, unlike `ModelCatalogService.refresh` (line 221) and
`ProviderRegistry.#probeConnectionKeys` (line 2094), which both honour `unsupported`.

Stored availability then outranks the allow-list at inference:
`provider-registry.ts:1601` returns `model_unroutable` when any key has a known list that lacks
the model, and `:1609` filters those keys out. A Provider configured `modelDiscovery: unsupported`
therefore has discovery state that gates routing anyway — which is what `muse` is stuck behind,
and why a relay host needed a Provider of its own rather than a Key on an existing one.

Two candidate fixes: skip availability writes when `modelDiscovery === 'unsupported'`, or let an
explicit `allowedModels` entry outrank stored availability. Not applied here — this run changed
prod data only, no code.

## Correction, same day: providers are per family, not per host

The first import created one Provider per relay host (`relay-<hostname>`). That
shape is wrong. The Owner's convention is one Provider per model family, with
each host attached as an Upstream Key.
