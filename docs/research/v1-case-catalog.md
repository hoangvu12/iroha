## Category key

| Cat | Meaning | What v2 should do |
|---|---|---|
| **a** | Essential behaviour any gateway like this must keep | Keep the behaviour (not necessarily the mechanism) |
| **b** | Provider or platform quirk (a specific upstream, Bun/Elysia, Cloudflare, browser) | Keep, but isolate in provider-specific code/data |
| **c** | Workaround for an earlier v1 design choice; disappears under a simpler model (reason given after " — ") | Drop the rule, but check the underlying (a)/(b) need is still met |
| **d** | Dead, unused, never-reached, or broken code/config | Don't port |

Some **a** rows are marked **v1 BUG/GAP**: things v1 gets wrong or never handles, found by reading code (not by running it; v1 tests use mock upstreams that accept whatever v1 sends). They are listed as requirements because "handle every real-world case" means v2 must get them right, not copy v1.

## Known overlaps between parts (same fact, different angle)

- Gateway Key only accepted as `Authorization: Bearer` (no `x-api-key`): REQ-06, KEY-03/04. A caller's `x-api-key`/`api-key` is not in `src/inference/blocked-headers.ts` and so can be forwarded upstream: KEY-05.
- Key test always sends `Authorization: Bearer`, so x-api-key providers fail it: PRV-34, FAIL-121 (`src/providers/key-probe.ts:66`).
- Multi-endpoint failover needs `retryAmbiguousNetwork=true`, which create ignores: PRV-16, FAIL-88.
- Discovered per-key model lists filter keys out, contrary to ADR-0023: MOD-20, FAIL-108 (`src/providers/provider-registry.ts:1630`).
- Z.ai `TIME_LIMIT` is the tool-call quota, not chat capacity: USE-04, FAIL-118.
- `connectionTimeoutMs` stored but never enforced: PRV-17, TIME-04.

## What the (c) rows mostly come from

1. **Five overlapping "can key K serve model M" sources** (Gateway Key scope model list, catalog row source, per-key allow/deny lists, per-key discovered availability, per-key rewrites); ADRs 0023/0029/0030/0031 are each a precedence rule between two of them (Part 3 preamble).
2. **Upstream Accounts** (legacy grouping, planned for removal) and the account Capacity Scope.
3. **Durable Key Health kept separately from capacity evidence/readings**, with reconciliation between them, plus provisional vs authoritative evidence.
4. **Dual SQLite/Postgres engines** and the connection→provider and handle-history migration conformance tests.
5. **Wire shape as template data / Pack indirection**, provider-level `capabilities` stored but never read, legacy scope array beside the access policy, management keys as one JSON blob in settings.
6. Create-vs-PATCH asymmetries (retry settings ignored on create, duplicate-provider dropping per-key settings).

# Request shapes & translation (REQ)

Scope: caller-facing surfaces, body/header forwarding, OpenAI Chat Completions, Responses, Anthropic `/v1/messages`, OpenAI↔Anthropic translation both ways, streaming, tool calls, reasoning, images, usage reporting, caller-visible error shapes, compression/CORS. Failure classification, retries, model identity, polling, gateway-key scopes, logging and timeouts belong to other parts and appear here only as cross-references.

Paths are relative to the repo root. `inference.ts` means `src/http/inference.ts`, `anthropic-adapter.ts` means `src/inference/anthropic-adapter.ts`, and `generic-adapter.ts` means `src/inference/generic-adapter.ts`.

Category key: **a** = essential behaviour; **b** = provider quirk; **c** = workaround for a v1 design choice; **d** = dead or unused (spec-only or never observable). Rows marked **v1 BUG/GAP** describe something v1 gets wrong or leaves out but that a v2 handling "every real-world case" has to get right. The mock-based tests miss these because the mocks accept whatever shape v1 sends.

# Model identity and catalog

Paths are relative to `C:\Users\ADMIN\Desktop\nguyenvu\iroha`. Cat: a = essential behaviour, b = provider quirk, c = workaround for an earlier v1 design choice, d = dead or unused.

Background for the (c) rows: v1 has **five overlapping sources of truth about "can key K serve model M"**: (1) the Gateway Key scope's model list, (2) the catalog row (`discovered` / `template` / `owner_added` / `excluded`), (3) the per-key `allowedModels`/`deniedModels`, (4) the per-key discovered Key Model Availability, and (5) the per-key `modelRewrites`. ADRs 0023, 0029, 0030 and 0031 are each a precedence rule between two of these. A v2 with one per-endpoint model list (gateway ID to wire ID) plus a provider-level "trust discovery? yes/no" flag would not need most of them, but it would still need the **behaviours** marked (a)/(b).

# Failure classification, retries, failover, Key Health, capacity scopes, routing eligibility

Scope: how v1 reads a failed upstream answer, what it writes to Key Health, how the retry loop picks the next attempt, and which keys are eligible. Paths are relative to the repo root. `inference.ts` = `src/http/inference.ts`, `registry` = `src/providers/provider-registry.ts`, `generic` = `src/inference/generic-adapter.ts`, `recon` = `src/providers/capacity-reconciliation.ts`.

Category key: **a** = essential behaviour; **b** = provider quirk; **c** = workaround for an earlier v1 design choice that would disappear with a simpler model (reason given after " — "); **d** = dead/unused.

A note on how the paths fit together. Every Attempt failure takes the same path: adapter `classifyFailure` returns {kind, capacityScope, retryAction, retryAfterSeconds, capacityEvidence?, diagnostics?}. Then `reconcileInferenceCapacity` runs (fresh usage authority), then `registry.recordInferenceFailure` (durable Key Health), then the retry loop acts on `retryAction`. Typed adapters wrap the generic one and override only what they recognise.
