# Bulk Key Import uses partial-success semantics and a dedicated endpoint

The Owner can paste or upload a batch of Upstream Keys (each optionally paired with its own base URL) at once. The Add provider and Add keys flows both expose a `single | bulk` mode toggle; the bulk mode lands in the same dialog through a shared `BulkKeyInput` component. The accepted input formats are CSV `upstreamKey,baseUrl` per line, pipe-separated `upstreamKey|baseUrl` per line (auto-detected per line by whether it contains `|`), and JSON arrays of `{upstreamKey, baseUrl?}` for file uploads with the `.json` extension. The server exposes a new `POST /providers/:id/keys/bulk` route that returns per-entry results: 200 with `{added: [{index, keyId}], failed: [{index, problems?}]}` on partial success, 400 `validation_failed` on whole-batch errors (empty list, more than 200 entries, malformed body), and the standard provider-level error responses (`provider_not_found`, `provider_archived`, `authentication_required`). We rejected looping the existing `POST /providers/:id/keys` from the client (O(N²) probe work because `#probeConnectionKeys` iterates every unverified key on each call, and any single error aborts the loop without per-entry reporting) and rejected atomic whole-batch validation (worse paste UX, no precedent in the OmniRoute / LiteLLM / Bifrost bulk paths). Each successful entry is audited as `key.created`; bulk-imported keys carry no per-key `accountId`, `allowedModels`, or `deniedModels` (Owner configures those via the existing Configure dialog after import). The cap of 200 entries per batch matches OmniRoute's `bulkImportProviderSchema.max(200)` and is enforced server-side.
