## Prompt caching across Shapes

**The conversation's ID, on every request.** When a request belongs to a conversation (its `affinity.source` is not `none`), Iroha sends the Provider a UUID made from it, the same value Conversation Affinity ranks keys by: one per conversation, Gateway Key, Provider and model, never the Caller's raw session string (many Endpoints are third-party relays). It goes, passthrough or translated, whatever the Shape:

- in the headers relays and Providers route a session by, `x-session-affinity` (Fireworks and others), `x-session-id` (OpenRouter) and `session_id` (Codex-style backends; a Caller's `session-id` counts as it), each only when the Caller did not send it;
- on OpenAI Chat and Responses Endpoints, as `prompt_cache_key` when the body has none. On passthrough that one appended field is the only change to the Caller's bytes.

A Caller's own `prompt_cache_key` or session header is forwarded as is, never replaced. `Iroha-Session` itself is never forwarded. Turns of one conversation then reach the Provider's (or relay's) machine or account that holds their cache.

Otherwise passthrough (the Endpoint speaks the Caller's Shape) sends the Caller's body byte for byte: cache markers, `user`, `metadata` and Gemini's `cachedContent` reach the Provider as written. When Iroha translates, it also adds what the Endpoint can use for its prompt cache:

- **Toward Anthropic Messages** (from Chat, Responses or Gemini), cache markers:
  - A Chat Caller's own markers, written as OpenRouter does (`cache_control` on content parts, on tools or on the request, `ttl` included), are kept on the blocks that carry the same text.
  - With no markers of the Caller's, Iroha adds them: Anthropic's own API (`api.anthropic.com`) gets the automatic top-level `cache_control`; other Endpoints get one on the last tool, the last system block and the last message. Kimi/Moonshot Endpoints get only one top-level marker (they refuse others); DeepSeek's get none (it ignores them).
  - Never more than 4 (the earliest are dropped), and never a 1 h marker after a 5 min one (it becomes 5 min), since Anthropic refuses both.
  - The cache writes this causes cost more than normal input once (1.25x for 5 min); the next turn reads them at about 0.1x. Translated answers now report writes to the Caller: OpenAI `prompt_tokens_details.cache_write_tokens` (Chat), `input_tokens_details.cache_write_tokens` (Responses), Anthropic `cache_creation_input_tokens` (with `input_tokens` the uncached part).
- **Toward OpenAI Chat from Anthropic Messages**: markers of messages are kept as before; the system prompt's markers are kept too (as text parts of the system message) where the Endpoint honours them: OpenRouter and Alibaba (Qwen) hosts, or `cache_markers: on`.
- **Conversation fields**: `user`, else `safety_identifier`, else `prompt_cache_key` becomes Anthropic's `metadata.user_id`; an Anthropic Caller's plain `metadata.user_id` becomes OpenAI's `user` (Chat and Responses; never replacing a `user` already there; Claude Code's value is a session, not a user, and is left out).
- **Refused**: Gemini's `cachedContent` names a cache stored at Google that no other Shape can read; translating would silently lose that context, so such a request gets `400 untranslatable_request` when only Endpoints of another Shape can serve. Send the cached contents in the request, or use a Provider with a Gemini Endpoint.

**Turning it off, per Endpoint** (`PATCH /api/providers/<p>/endpoints/<e>`): `cache_markers` (`""` Iroha's default for the Shape and host; `on`: markers whatever the host, toward Anthropic on the last tool, system block and message, and the Endpoint's `caching.summary` warns where the host is known to refuse them (Kimi/Moonshot) or ignore them (DeepSeek); `off`: no markers at all) and `send_prompt_cache_key` (`""` default: on, except no body field to hosts known to refuse unknown fields such as Google's and Mistral's OpenAI APIs, which still get the session headers; `on`; `off`: no `prompt_cache_key`, no session headers and no `user` added, so passthrough is byte for byte again). The Endpoint's `caching` (`markers`, `prompt_cache_key`, `summary`) says what its requests get.

**An Endpoint that refuses these fields** (a 400 or 422 saying `cache_control`, `prompt_cache_key`, `metadata` or `user` is unknown: "Unrecognized request argument supplied", "Unknown parameter", "Unsupported parameter", "unknown field", "Unknown name", or "Extra inputs are not permitted" for that field) is asked again at once, on the same key, without anything Iroha added, and gets nothing added for the rest of the Request. On passthrough, where the appended `prompt_cache_key` is the only difference from the Caller's request, any 400 or 422 the Failure Rules would end the Request with is asked again the same way, whatever its wording; one the rules read as the key's or model's (billing, a Model Gap) is handled as usual. That retry is free: it is recorded as its own Attempt (the first shows outcome `retry_elsewhere` and why; the key's state is unchanged) but does not count toward the Provider's `max_attempts`, and is made at most once per Endpoint. When the retry fails too, you get its answer. On translated requests any other 400, even one quoting such a field (a role error naming `user`, a Provider echoing the request), goes to the Failure Rules as usual. Session headers stay on the retry. Set the Endpoint's setting `off` to skip the extra Attempt.
